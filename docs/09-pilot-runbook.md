# Pilot service runbook (W13) — DineReserve

The pilot is one real dinner service run with a partner restaurant on top of the
deployed build, with the paper/telephone process kept as a fallback. The goal is
not to prove the software again — the 199 automated tests do that — but to find
the operational gaps that only show up on a real floor: who presses what, when the
host is busy, and what happens when something fails mid-service.

The rehearsal in this repository (`php bin/pilot.php`) replays the same service
against a disposable copy of the demo restaurant, so the team can practise the
runbook before the restaurant does.

## Scope

| Item | In scope | Out of scope |
|---|---|---|
| Service | One dinner service (17:00–22:00), 12 tables, ~48 covers | Multi-day operation, lunch service |
| Booking channels | Online, phone, walk-in, waitlist | Third-party platforms |
| Staff | Host desk (1), duty manager (1), kitchen (informational) | Full POS integration |
| Data | Demo restaurant seeded with the real floor plan | Live payments, loyalty |

## Pre-pilot checklist (T-3 days to T-1 hour)

- [ ] Restaurant profile, service periods and the **real** table plan loaded (60 tables / 3 periods in the demo).
- [ ] `settings` reviewed with the manager: slot minutes, window, cut-off, turnover buffer, waitlist offer TTL, max party.
- [ ] Users created for the host and manager with the right roles (`bin/admin.php create`), passwords changed from the demo value.
- [ ] Backup taken and **verified** (`bin/pilot.php --backup=…` or the W12 drill); restore steps printed and kept at the host desk.
- [ ] Devices: one tablet/laptop for the host, one for the manager, both on the restaurant Wi-Fi; the floor plan screen open.
- [ ] `ADMIN_TOKEN` set on the deployment (never the demo default) and the token held by the manager only.
- [ ] Notifications checked: a test booking sends the confirmation to a real mailbox; the mail log is visible.
- [ ] Staff briefing (20 min): creating a booking, seating, walk-in, no-show, waitlist offer, cancelling, what to do when the screen is wrong.
- [ ] Rollback rehearsed: everything on paper, then re-enter the bookings after service.
- [ ] Team on site 90 minutes before opening; go/no-go call at T-60.

## Service-day timeline

| Time | Activity |
|---|---|
| 16:00 | Arrive, deploy the frozen tag, seed/verify the floor plan, check the backup |
| 16:30 | Walk the floor with the host: table codes, statuses, cleaning flow |
| 17:00 | Open: host takes phone bookings in the system, not the paper book |
| 17:30 | First walk-in; observe the status change and the cleaning cycle |
| 18:30 | Check the notification queue: everything sent, nothing failed |
| 19:00–20:30 | Peak: bookings, seating, waitlist offers; engineer watches the API error log |
| 21:00 | No-shows marked, tables released, report pulled for the manager |
| 22:00 | Close: export the day report (XLSX + PDF), snapshot the database, debrief |

## Monitoring during service

| Signal | Where | Action |
|---|---|---|
| Floor plan freshness | Screen polls every 5 s | If stale > 30 s, refresh; if it persists, switch to paper |
| Booking errors | API responses / server log | Any 5xx → note the reference, retry once, then paper |
| Notification queue | `notification_log` (sent/failed/queued) | Failures should retry at 1/5/15 min; check after the peak |
| Waitlist offer expiry | Offer is valid 5 minutes | If the guest calls late, re-add them to the queue |
| Report totals | End-of-service report | Compare covers with the kitchen's count |

## Rollback

1. Announce to the host: "back to paper" (one phrase agreed in the briefing).
2. Stop taking bookings in the system; use the paper sheet.
3. Keep the system running for reporting — do not delete anything.
4. After service, re-enter the bookings taken on paper and mark the ones the system missed.
5. Restore the pre-service backup only if data is corrupted (steps: stop the app, copy the backup over the live file, restart, verify with a known reference).
6. Record the incident and the trigger in the post-pilot review.
